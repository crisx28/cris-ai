01

What stays the same

The view doesn't change shape. Rows are clients, columns are dates, each build is still four segments — scope call → SOW due, pre-build wait, the fixed 2-week build, then 4 weeks of refinement. What changes is where the dates and states come from: today someone types them in; after this, three feeds populate and update them, and a person still drags to adjust.

Correction, not an addition — there are no milestones on this calendar, by design. An earlier pass here inferred "handles milestone events at some level" from a commit subject, not from reading the file; the truth is the opposite. Six milestone kinds — kickoff, build end, scope call, SOW due, access ready, handover — were removed entirely on 31 Aug, on Jack's own instruction: each sat on a day a phase bar already covered, so a milestone forced a second calendar row for information already shown, not new information. Each bar exists only if the dates it needs are filled — a bar whose dates go missing is deleted from the calendar, not left blank or wrong, and deliberately so: the sync walks the union of what should exist against what previously existed, and removes anything no longer supported.

Why this outranks a wrong-date bug, not just why it's severe: a wrong bar gets reported by whoever notices it looks off. A bar that silently stops existing is indistinguishable from a build that was simply never scheduled — on the one calendar view Jack invited the whole team to. Invisibility, not severity, is the reason this raises section 09's ownership gap rather than just adding to it.

The exposure is wider than one field. Pre-Build needs both sow_due_date and access_ready_date — blank access_ready_date loses only Pre-Build, but blank sow_due_date loses Pre-Build and the Scope bar, since the two share it. So the single field with the most riding on it is sow_due_date, not the unowned one — worth weighing against section 09's ownership list, not a replacement for it.

A third, different failure mode, run rather than reasoned about, with a passing control on complete dates: if start_date is set and build_end_date is blank, the date helper throws — and it throws outside the sync's per-event error handling, so the whole row's calendar sync aborts, including bars that were otherwise fine. Not a disappearance and not a wrong date: a build that should show three good bars can show none.

Unmeasured, and reported as unmeasured rather than as zero: whether any live row is currently in that throwing state. The Build Schedule endpoint returns Unauthorized on this check, so an empty result here reflects a permissions wall, not an absence of the condition — no count either way, don't read a zero into it.

03

Stage automation

Two stores, two different jobs: the build record is the source of truth for the client; the Build Schedule table is the source of truth for the schedule. 20 rows today, hand-entered or dragged — not read off the build record wholesale. Only two things cross from the build record into a row: the client's name, once linked, and the scope-call date, where one's been recorded (11 of 20 carry one). Everything else on the table lives there natively.

The coloured bars themselves are calculated, never stored: build is a fixed 2 weeks, refinement follows for 4, scope call → SOW due is 5 days, and Pre-Build runs from SOW due to access-ready. A date that's pinned or dragged is marked manual and the system won't move it again; left untouched, it stays derived and recalculates off whatever's upstream.

↳

Standing rule, not a per-field decision: once a build-record field has a named writer and real data in it, it syncs onto the Build Schedule table automatically and the bar moves with it — nobody has to also update the Gantt by hand. That's already true for scope_call_scheduled_at and lead_builder. It becomes true for access_ready_date the moment someone is named to write it — that's the only blocker, not a separate design question each time a field gets added. Entering data at the source is what makes the schedule move; nothing else has to change for that to happen.

Deriving contract_status — five things that cost a day if missed

Two of these produce a confident wrong answer, not an error — worse than a crash, because nothing flags it.

  1. The join key changes name. build.sow_id joins to the signing store's token column, not its id. Joining on id silently returns a 100% failure rate — every build DANGLING, every document orphaned. A round number like that is the tell, not a real result. Validate any join with a control pair: one known-good token, one invented one — it discriminates instantly.
  2. The status vocabulary is exactly four values, nothing else: draft, sent, signed, voided. Measured live across all 46 documents: draft 24, signed 10, voided 7, sent 5. Don't invent a fifth, and don't remap onto one that isn't there.
  3. Three outcomes, not two. UNKNOWN covers no sow_id at all (14 of 20). But a sow_id that points at no document is a different, distinct fact — DANGLING, currently one real case (Julio Rojas). "Nobody recorded a contract" and "the pointer is broken" must render as different states, or the one that's an actual bug hides inside the one that's expected.
  4. template can be null on a legitimately sent document. Dan White's contract is a hand-typed override with no template recorded. Anything downstream that keys off template name will misread a real, valid contract as malformed.
  5. Inverse checked, so it doesn't need re-checking: 11 of 15 non-test signed/sent documents aren't reachable from any build record. Not a gap — 5 are payment/contract test fixtures, 6 are HR documents (contractor NDAs, letters of offer). No client contract is hiding outside the build records.

05

Capacity signal — flag only, never a proposed date

This is about projects, not Jack's diary. Moving a kickoff is a commercial act, not something a view does on its own — so this reports open windows, it never writes one in as an answer. "Full" is confirmed as of tonight's ruling: 2 concurrent build phases, and refinement doesn't count toward it — Polly measured 3 refinements running at once with nobody treating the board as blocked, so a bar in refinement is background noise to this check, not a conflict.

// pseudocode, not literal API — output is informational only for day in today...horizon(16 weeks): window = [day, day + 2 weeks] // fixed build length concurrent = count of other builds whose BUILD phase only (not refinement) overlaps window if concurrent >= capacity_threshold: continue // default 2, configurable — Feed D if window overlaps Jack's real OOO/vacation (Feed C): continue if day < earliest_ready(client): continue // scope call + SOW + access lead time yield window to the open-window list — never auto-applied to a bar

If no client is yet linked, this just reports the next N open windows against Feeds A–D so sales can quote a realistic kickoff date on the scope call — this is the "clear indicator / forecast" piece: capacity becomes visible before anyone commits to a date. A person still types the date into the Build Schedule table by hand; the signal never fills it in. capacity_threshold is a stored setting defaulting to 2, not a hardcoded number — it needs to move without a code change if the real limit turns out to be different.
